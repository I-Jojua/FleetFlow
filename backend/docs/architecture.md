# Architecture overview

```text
HTTP client
  └─ Express app
      ├─ request ID + request metrics/logging
      ├─ Helmet, configured CORS, JSON parsing
      ├─ route middleware (rate limit, auth, role checks, validation)
      ├─ controllers
      ├─ module services
      │   ├─ Prisma PostgreSQL client
      │   ├─ Redis shared rate-limit store
      │   ├─ Redis Pub/Sub for cross-instance GPS fan-out
      │   └─ best-effort notification / Slack integration
      ├─ BullMQ queue producer
      │   └─ centralized demo and auth-email queues over validated REDIS_URL
      └─ safe error handler

Separate worker process
  └─ BullMQ Worker (dedicated blocking Redis connection)
      ├─ typed demo job processor
      └─ auth-email processor → AES-GCM token decrypt → provider adapter
      └─ PostgreSQL outbox poller → stable auth-email BullMQ jobs
      └─ GPS history retention worker
```

## Modules

- **Authentication:** controllers validate requests, services manage password hashing, JWT access tokens, refresh-token rotation and revocation. Bearer authentication loads the active user and the role middleware restricts staff and driver operations.
- **Authorization:** roles come from the current active user row, never from caller-controlled JWT role claims or request bodies. Route-level role checks are paired with service/database ownership predicates for customer deliveries, assigned driver deliveries, GPS reads/writes, and per-user notifications. See [authorization matrix](authorization-matrix.md) for the complete mounted-route policy. An authenticated caller outside a delivery's ownership scope receives the same 404 as an unknown delivery on detail and GPS read endpoints.
- **Deliveries:** routes select public tracking or authenticated operations. Controllers enforce caller/resource ownership; services implement creation, state transitions, assignment, event persistence and location history.
- **GPS tracking:** the authenticated driver identity comes from the database-backed access token, never request payload. Location writes are rate-limited, validate coordinate ranges and source timestamps, reject old/future and out-of-order reports, and serialize samples per driver in a PostgreSQL transaction. The sample commits before bounded best-effort Redis publish, so Pub/Sub failure cannot undo history or indefinitely hold the request. Existing composite indexes support latest-per-delivery/driver and date-bounded history; page size is capped at 100 and explicit date ranges cannot exceed configured retention. Latest-location responses include age and a configurable stale flag; stale indicates age only and is not a coordinate-accuracy guarantee. GPS ingestion count and database processing duration appear in protected metrics. The worker prunes rows after `GPS_LOCATION_RETENTION_DAYS`.
- **Real-time delivery tracking:** `POST /api/v1/realtime/ticket` exchanges an authenticated access token for a random, 30-second, one-use Redis ticket; Redis `GETDEL` makes concurrent consumption single-winner. The WebSocket upgrade consumes it and loads the active database role. Pending and active connections count against per-process and per-direct-peer-IP caps. Delivery ownership/driver assignment is rechecked against PostgreSQL before each broadcast. Each process caps WebSocket buffered bytes and closes slow clients rather than growing memory without bound. GPS events cross API instances over a dedicated reconnecting Redis Pub/Sub connection. Pub/Sub is transient: events published while an instance is disconnected are not replayed. PostgreSQL history remains authoritative; clients reconnect with a new ticket, resubscribe, and use REST to recover state. The protected metrics endpoint reports active connections/subscriptions, rejected upgrades, Pub/Sub connections, publish outcomes, and backpressure. These limits/counters are process-local; use proxy-level global controls and an external metrics aggregator for deployment-wide operations.
- **Active driver locations:** staff-only `/api/v1/drivers/active-locations` uses PostgreSQL `DISTINCT ON` to select each active driver's latest location for an assigned or in-progress delivery before pagination. It does not load all drivers or expose their profile details.
- **Driver workforce:** `User.availability` tracks AVAILABLE, UNAVAILABLE, ON_BREAK, OFF_DUTY, and SUSPENDED independently from account status. Drivers may have non-overlapping scheduled/active shifts with an IANA timezone label, verified qualifications with expiry dates, and a current vehicle assignment backed by append-only assignment history. Delivery requirements can specify an exact vehicle type, minimum payload/volume, refrigeration, and qualification codes. A driver cannot be deactivated or operationally suspended while active deliveries remain; vehicle changes and shift edits/cancellations are blocked where they could strand active work. PostgreSQL advisory locks serialize driver availability, shift edits, vehicle changes, and dispatch assignments by the same driver key. Vehicle assignment uniqueness is also enforced by partial unique indexes.
- **Dispatch recommendations:** staff can request bounded advisory candidates at `GET /api/v1/dispatch/deliveries/{id}/recommendations`. A bounded PostgreSQL query reads a repeatable-read snapshot and requires active account, AVAILABLE status, a current ACTIVE shift, current ACTIVE assigned vehicle satisfying the delivery requirements, verified/unexpired required qualifications, a fresh GPS point, and workload below `DISPATCH_MAX_ACTIVE_DELIVERIES`. Missing pickup coordinates prevent recommendations; missing/stale driver GPS excludes that driver. Missing vehicle, qualification, or active shift data also excludes the driver. Results include only driver IDs and operational score details; GPS coordinates and profile/contact fields are never returned. The score combines straight-line distance, workload, GPS freshness and capacity utilization. Weights are configurable percentages and must sum to exactly 100; defaults are 60/25/15/0, preserving the P6.1 ranking. Distance is a Haversine approximation, not road distance or ETA; capacity fit is based on requested-to-available capacity and is a heuristic. Equal scores use ascending driver UUID for deterministic ordering. Recommendations never assign. The assignment transaction rechecks account, availability, workload, shift, qualifications, vehicle status/capability and persists the chosen vehicle ID under the per-driver PostgreSQL advisory lock, so a prior recommendation does not reserve availability. If pickup coordinates are absent, direct staff assignment remains possible and GPS freshness is not required; a recommendation cannot be requested for that delivery.
- **Geospatial scope:** no PostGIS or road-routing service is used. Distance scores are decision support only; distance normalization is not a hard radius.
- **Drivers and customers:** their services own account creation, profile/list queries, status updates and status-specific statistics.
- **Notifications:** records belong to a user and may refer to a delivery. Delivery workflows persist notifications best-effort; Slack alerts are also best-effort.
- **Health and operations:** liveness is independent of dependencies; readiness probes PostgreSQL and Redis. In-process metrics are available only with the metrics bearer token. Graceful API shutdown stops WebSocket upgrades and closes connected clients before releasing Redis.
- **Documentation:** the OpenAPI 3.1 document is checked in at `backend/docs/openapi.json`. Swagger UI is available in development; production docs are disabled by default and token-protected when enabled.
- **Background jobs:** the API process owns the centralized BullMQ producer registry. Worker processes start separately with `npm run worker` and consume the same registered queue names using validated `REDIS_URL`. BullMQ creates role-appropriate Redis connections because blocking worker connections need different retry settings from the low-latency API Redis client. Submission resolves only after Redis acknowledges the job; failures propagate to the caller. Jobs use exponential retries and bounded completed/failed retention. Processing is at-least-once, so future business processors must be idempotent. Worker SIGTERM/SIGINT handlers stop new work and drain active jobs within the configured shutdown timeout.
- **Authentication emails:** registration, verification resend, and password-reset requests write their single-use token and an encrypted outbox event in the same PostgreSQL transaction as the associated account/token operation. The outbox dispatcher resolves the current recipient from the referenced account, decrypts the email token in memory, and enqueues it into the existing BullMQ email queue with a stable token-based job ID. The email worker then renders centralized HTML/text templates and calls the selected provider. PostgreSQL stores only SHA-256 token hashes in `AuthToken`; outbox payloads contain AES-256-GCM ciphertext, never plaintext tokens or email addresses. The encryption key must be provisioned consistently to API and worker services. The development `console` provider deliberately reports that mail was not delivered. Outbox enqueue attempts retry exponentially and recover stale processing leases; queue and provider delivery are at-least-once, not exactly-once.
- **Audit logs:** action names include `dispatch.recommendations` alongside auth, account, customer, driver, and delivery operations. `AuditLog` records authentication outcomes, account creation/status changes, driver/customer changes, delivery operations, and staff recommendation requests. Successful critical writes and recommendation reads insert their audit row in the same PostgreSQL transaction. Failed sign-in and rejected verification/reset tokens create awaited anonymous/security audit records separately because no successful business transaction exists. Actor role is snapshotted; deleted users leave audit records with a null actor reference. Metadata is restricted to an allowlist of enum-like state/reason values and changed field names. IP is stored only for authentication/security events and privileged administrative changes, taken from Express's trusted `req.ip` after proxy settings and IP validation. `GET /api/v1/audit-logs` is read-only, paginated, filtered, rate-limited and restricted to ADMIN/SUPER_ADMIN; no public mutation or single-record endpoint exists.

Audit logs are ordinary PostgreSQL records with indexes and foreign-key behavior, not cryptographically signed or tamper-proof. Database administrators can still alter them. Set retention, archival, access review and backups according to policy; this application does not automatically delete audit history. User role changes are not audited because the current API has no role-change operation.

Role permissions are defined at the route layer and verified against database-backed integration tests for identity, role spoofing, inactive accounts, and nested delivery/location ownership. This is application authorization and does not prevent privileged database operators from bypassing it.

Idempotency applies only when a client opts in with `Idempotency-Key` on delivery creation or driver assignment. Keys are scoped to actor and operation, stored only as hashes with a canonical request fingerprint and a reference to the result resource, and expire after the configured retention period. PostgreSQL transaction advisory locks serialize same-key concurrent retries. Replays return the resource referenced by the committed result; the response body is reconstructed from current database state and is not stored as a potentially sensitive snapshot.

The transactional outbox has `PENDING`, `PROCESSING`, `COMPLETED`, and `FAILED` states. Each claim increments attempts and sets a lease; stale leases are reclaimable after worker crashes. Transient queue submission failures are rescheduled with exponential backoff and permanent failures retain a safe error class for operator review. Completed rows have their encrypted payload cleared. BullMQ stable job IDs deduplicate while a job record is retained, but Redis enqueue and PostgreSQL completion are not one atomic transaction; delivery is at-least-once and downstream email providers may receive duplicates after a crash at the acknowledgement boundary. There is no exactly-once guarantee.

## Observability boundaries

Request logs include a generated request ID, method, route template, response status and duration. Query strings, route parameter values, body content, IP addresses and raw error objects are not logged. Request IDs flow through asynchronous work using `AsyncLocalStorage`.

Metrics are in-memory process-local aggregates with no user, IP, path, or delivery labels. Request counts, status counts, errors and duration summaries reset when the process restarts. Realtime counters likewise reset on restart and are not aggregated across instances by this endpoint. Database and Redis availability show the last observed probe/limiter result and can be `unknown` until observed. Use a metrics collector or external monitoring for durable history and cross-instance aggregation.
